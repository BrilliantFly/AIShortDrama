# 主流生图 / 生视频 ComfyUI 工作流调研

> 调研日期：2026-11-26
> 范围：文生图（T2I）、图生图 / 图像编辑（I2I）、文生视频（T2V）、图生视频（I2V）及首尾帧、多帧参考、视频编辑、闭源 API 接入。
> 口径：只写 **ComfyUI 里实际能落地**的模型与节点路线；模型版本与授权变动快，落地前以各官方仓库为准。凡标注「实测」的数据来自第三方公开横评，非本机复测。

---

## 一、结论摘要（先看这段）

1. **图片端已经换代**：2026 年的默认答案不再是 SDXL，而是 **Z-Image Turbo（快 / 中文 / 8–16G）** 与 **FLUX.2 / Qwen-Image（质量 / 文字 / 24G）** 双档并行。仓库现役的 ZImageTurbo + QwenEdit 组合方向正确，缺的是 FLUX.2 这条高质量线。
2. **视频端「求稳选 Wan，写实选 Hunyuan，求快选 LTX」**：开源阵营里 **Wan2.2** 生态最全（T2V/I2V/首尾帧/S2V/VACE 全有、Apache 2.0 可商用），**HunyuanVideo-1.5** 写实人像与轻量占优，**LTX-2.5** 快且唯一原生音画同步 + 多镜头。
3. **本仓库主力 H3 是另一条赛道**：MiniMax H3 以 **音画同出 + 多参考锁身份（Ref2VA）** 见长，正好覆盖漫剧「对白 + 角色一致」两个硬需求；本地可跑（最低约 12G），闭源 API 也可在 ComfyUI 节点里调。它是仓库已有资产，仍是本生产线的最优主线，不应被 Wan/LTX 替换，只应作为**补充引擎**。
4. **图像编辑的正确解法变了**：从「IPAdapter + ControlNet 软约束」升级到 **Qwen-Image-Edit / FLUX.1 Kontext 指令式编辑**——一句话改图且身份保持更强，16G 卡实测 Qwen-Edit 27.2s / Kontext 53.3s。
5. **一致性仍然是分层解决**：主角用 LoRA（权重级），配角用 IPAdapter/PuLID（参考图级），场景/道具用固定板卡 + 固定种子；没有单一方案能通吃。
6. **长视频一律拆段**：无论哪家模型，超过 5–6 秒都会掉质量；工程共识是 5–15 秒逐镜生成 + 尾帧锚定续接。这与本生产线既有的「≤144 帧拆段 + 尾帧锚定」纪律完全一致。

## 三、文生图 T2I

### 3.1 主流模型定位

| 模型 | 参数 / 架构 | 显存门槛（量化） | 特点 | 授权 |
|---|---|---|---|---|
| **Z-Image Turbo** | 6B | FP8 约 8G；BF16 14–16G；量化最低 6G | 速度最快（4090 上 1024² 约 2.3–3s），中英双语文字 WER 0.072 领先，适合批量草稿 | 可商用 |
| **FLUX.2 klein 4B** | 4B | 约 13G | 16G 甜点档，可商用 | 可商用 |
| **FLUX.2 dev** | 32B | 量化 18–24G；原生更高 | 画质上限高，原生 4MP、32K token；4090 上 1024² 约 42s；手部准确率 92%（Z-Image 86%） | **非商用**，销售需单独授权 |
| **Qwen-Image** | 20B 级 | 完整版约 24G；GGUF 约 8G 起 | 中文文字渲染强、编辑生态好 | 一代 Apache 2.0；**2.1 非商用** |
| **SD3.5** | DiT | FP8 16G 可跑 batch 3–4 | 节点 / LoRA / 后处理生态最成熟 | 商用需看 Stability 条款 |
| **GLM-Image / 混元 2.x** | 大参数 | 16G+ 量化 | 中文语义强；混元开源版配 byt5-sm + Qwen2.5-VL 双文本编码器 | 以各仓库为准 |
| **即梦 Seedream / 通义万相** | 闭源 | 无本地权重 | 中文语义、本土风格、角色一致性稳定；国内 API 延迟低 | 按平台条款 |

### 3.2 标准 ComfyUI 节点链（T2I 通用骨架）

```
Load Checkpoint / UNET Loader
  ├─ MODEL ───────────────► KSampler(model)
  ├─ CLIP ──► CLIP Text Encode(positive / negative) ──► KSampler(conditioning)
  └─ VAE ─────────────────► VAE Decode(vae)
Empty Latent Image ───────► KSampler(latent) ──► VAE Decode ──► Save Image
```

**口径要点**：MODEL / CONDITIONING / LATENT 三类不能交叉接；negative 不接会明显出怪图；VAE 尽量与 checkpoint 配套，乱换会发黑泛灰。模型放 `models/checkpoints`、`models/vae`、`models/loras`、`models/controlnet`，文件名带版本标识（如 `z-image-base.safetensors` / `z-image-turbo.safetensors`）避免工作流匹配错。

### 3.3 8–16G 显存的现实做法

- 启动加 `--lowvram` / `--medvram`，注意力用 pytorch cross-attention。
- 全程 FP8 / GGUF 量化，显存降 40–50%，画质肉眼差异很小。
- 先 512–768 出草稿，确认构图后超分；不要硬拉 2K。
- 批量时优先加大 `batch count`（顺序）而非 `batch_size`（并行），并开启「跳过已生成文件」断点续跑。
- ControlNet 用哪个加载哪个，不用的从显存卸载。

## 四、图生图 I2I / 指令式编辑

### 4.1 两条路线

| 路线 | 代表 | 做法 | 优势 | 短板 |
|---|---|---|---|---|
| **传统重绘 / 控制** | VAE Encode + KSampler denoise、ControlNet（OpenPose/Canny/LineArt）、IPAdapter/PuLID/InstantID | 参考图 → latent 或身份条件 → 重绘 | 可控构图/姿态，节点生态最全 | 身份是软约束，多角度易漂 |
| **指令式编辑** | Qwen-Image-Edit 2511、FLUX.1 Kontext | 图 + 一句自然语言指令 → 编辑结果 | 零训练、身份保持强、可多图上下文 | 单图改动幅度有限，需写清「什么不动」 |

### 4.2 16G 实测横评（RTX 5060 Ti，1024²，同图同指令，seed 42）

| 方案 | 单次耗时 | 峰值显存 | 模型文件 | 授权 |
|---|---|---|---|---|
| Qwen-Image-Edit 2511 GGUF Q4_K_M + 4-step Lightning LoRA | **27.2 s** | 15.9 G | 13.2 G | **Apache 2.0** |
| FLUX.1 Kontext [dev] FP8 | 53.3 s | 15.0 G | 11.9 G | 非商用 |
| FLUX.1 Kontext [dev] GGUF Q8_0 | 82.1 s | 15.5 G | 12.7 G | 非商用 |

**关键坑**：Qwen-Image-Edit 走官方 40 steps + CFG 4 时双份图像占显存，16G 卡会触发 Windows Sysmem Fallback，实测 20 分钟仍不出图；**挂 4-step Lightning LoRA 后同图 27 秒**。Kontext 小 GGUF 可低至 7G 起跑，Qwen-Edit 需 11G+。带画面文字（招牌 / 标签 / 海报）优先 Qwen-Edit——它的文本编码器是 7B VLM，能读输入图上的字。

### 4.3 Kontext 多图参考的工程陷阱

1. **不要 stitch 拼图**：把多张参考图像素拼接再统一编码，模型会把拼接边界当图像内容，身份融合会脏；应分别编码为 latent，在序列维拼接并给 image ids。ComfyUI 用 `ReferenceMultiLatent` / `Set Reference Latent` 系列节点。
2. **参考图分辨率对齐模型预设**：Kontext 预设从 672×1568 到 1568×672，含 1024×1024；超出覆盖范围身份保持下降。
3. **输入顺序有意义**：多图顺序与 id 分配会影响「哪张图在哪被引用」。

### 4.4 漫剧出图的实测参数口径

| 参数 | 建议值 | 理由 |
|---|---|---|
| 分辨率 | 竖屏 576×1024 / 横屏 1024×576，同集不换 | 风格稳定 |
| sampler / steps | euler a 或 dpmpp_2m_sde，22–28 步 | 漫剧够用 |
| CFG | 5–7 | 过高易畸形 |
| denoise | 0.4–0.55 | 分镜迭代留改动空间 |
| IPAdapter weight | 0.65–0.75（连续分镜 0.75） | 1.0 会像复印、画面僵硬 |
| ControlNet strength | < 1.0，双控（姿态 + 轮廓）优于单控 | 锁肢体 + 锁构图 |
| seed | 同集固定 | 换 seed 五官会微调 |

**一致性分层**：主角训练 LoRA（30 张左右多角度、1024 统一、2000 步上下、权重 0.7–0.9），特写再叠 PuLID/InstantID 双保险；配角用一张角色卡 + 定妆图靠参考注入；风格用统一风格 LoRA 锁调性。多角色同框避免多 LoRA 同时挂载「串味」，优先分层合成。

## 五、文生视频 T2V

### 5.1 三大开源主力

| 模型 | 架构 | 显存门槛 | 定位 |
|---|---|---|---|
| **Wan2.2**（阿里） | 14B 双专家 MoE + 5B 混合 | 5B 约 8G；14B 量化 16G 级，24G 放手 | **生态最全的默认答案**：T2V/I2V/首尾帧/S2V/Animate/VACE 全覆盖，Apache 2.0 可商用，中文提示词原生友好 |
| **HunyuanVideo-1.5**（腾讯） | 8.3B DiT | 官方最低 14G + offloading | 轻量高性能，写实人像占优；约 5s@24fps，480P/720P 原生可超分至 1080p；训练代码开源便于 LoRA |
| **LTX-2.5**（Lightricks） | 22B（推荐蒸馏版） | 16G 起（FP8 预览），BF16 约 43G | **开源阵营唯一**一次生成多镜头连续叙事 + 音画同步 + 4K HDR；年营收 <1000 万美元免费商用，企业需谈 |
| FramePack | Hunyuan 生态封装 | 6–12G 可低分辨率 | 低显存长镜头续帧，适合一张角色图持续动 |

其他：SkyReels（影视镜头感）、MAGI-1（自回归续写）属特定场景补充，新手先跑通主力。

### 5.2 16G 卡同机实测对比（ComfyUI v0.24 便携版，RTX 4080S 16G）

| 模型 | 耗时（含加载） | 分辨率 × 帧 | 画质 | 显存压力 |
|---|---|---|---|---|
| Wan2.2-5B | 44.1 s | 832×480 ×49 / 2s | 锐利、细节丰富 | 轻松 |
| LTX-Video 2B | 28.1 s | 768×512 ×97 / 4s | 偏柔、细节略少 | 最轻松 |
| HunyuanVideo 720p | 156.1 s | 848×480 ×49 / 2s | 好、暖调 | 需 fp8 + 大量 offload，吃力 |

**10 秒 I2V 加赛（同一首帧）**：Wan2.2-5B 121 帧@12fps 耗时 70s，主体保真全程清晰；LTX-2B 241 帧@24fps 耗时 58s，中段更丝滑但**主体漂移、后 1/3 崩坏**。结论：16G 卡保留 Wan2.2-5B 主力 + LTX-2B 备选。

### 5.3 显存分档速查

| 显存 | 推荐 |
|---|---|
| 8G | Wan2.1 1.3B、Wan2.2 5B GGUF、FramePack |
| 12–16G | Wan2.2 14B GGUF、HunyuanVideo-1.5（offload）、LTX FP8 预览 |
| 24G | Wan 5B 全精度 / 14B FP8、LTX FP4；T5/UMT5 文本编码器建议挪到内存 |
| 32G+ | 720p FP8 通吃 |

**系统要求**：视频模型对内存比图像更敏感，offload 时 32G 内存是底线、64G 舒适；NVMe 必备（模型几十 G，慢盘每次切换多等几分钟）。

## 六、图生视频 I2V / 首尾帧 / 参考生视频

### 6.1 三种关键帧驱动形态

| 形态 | 输入 | 提示词对齐指令（H3 官方语法） | 用途 |
|---|---|---|---|
| **I2VA** | 只有首帧 | `For the target video, at 0.00 seconds into the target video, (from [Shot 1]) is fully referenced.` | 静帧转镜头，角色一致性要求高 |
| **FL2VA** | 首帧 + 尾帧 | `Picture 1 (from Shot 1) aligns with the 0.00-second mark ...; Picture 2 (from Shot N) aligns with the S.SS-second mark ...` | 可控起止的过渡；**倾向单一镜头连续插值**，不写多镜头 |
| **L2VA** | 只有尾帧 | `(from [Shot N]) aligns with the S.SS-second mark of the target video.` | 收拢到指定结果帧 |

H3 官方约束：首帧必填、尾帧可选；两帧同宽高比，各边 256–5760px，比例 2:5–5:2；输出短边 768 上限、32 的倍数；时长对齐 **17k+5 帧**网格。这些与本项目既有门禁（`check_segment_length.py`）一致。

### 6.2 MiniMax H3 六模式（本仓库主力）

ComfyUI 官方模板 / 导演台节点提供：

| 文件 / 模式 | 扩散模型 | 用途 |
|---|---|---|
| `minimax_h3_director_t2v.json` (T2V) | fl2va | 文生音视频 |
| `minimax_h3_director_fl2v.json` (FL2V / I2V) | fl2va | 首尾帧；只放首帧即 I2V |
| `minimax_h3_director_r2v.json` (R2V) | ref2va | 图片 / 视频 / 音频参考生视频 |
| `minimax_h3_director_v2v.json` (V2V) | ref2va | 按源视频时间轴逐段编辑 |
| `minimax_h3_director_rv2v.json` (RV2V) | ref2va | 源视频 + 参考图/音频，视频换人 |

R2V 限制：**最多 9 张参考图、3 段参考视频、3 段参考音频**；视频/音频每段 2–15 秒、总时长各封顶 15 秒；参考视频 23.976–60 FPS；参考音频必须有至少一个参考图/视频作视觉锚点。提示词里用 `Image 1` / `Video 1` / `Audio 1` 按顺序引用，并给每个参考分配任务（身份 / 风格 / 运动 / 音色）。

### 6.3 开源 I2V 的替代路线

- **Wan2.2 I2V / FLF2V**：质量与稳定兼顾，社区模板最多；16G 用 5B。
- **Wan VACE**：参考重绘 / 视频编辑，适合已有视频的局部改。
- **HunyuanVideo I2V**：写实人像优；注意本仓库的 720p T2V 版本不原生支持 I2V，需换 I2V 权重。
- **LTX I2V**：快，但长段漂移（见 5.2 实测）。
- **FramePack**：一张图续帧，低显存长镜头。

### 6.4 续接纪律（跨模型通用）

> 超过 5–6 秒必须拆段：上一段末帧 → 下一段首帧，尾帧锚定续接。

这是 Wan / Hunyuan / LTX / H3 的共同经验，也是本项目 `≤144 帧拆段 + 尾帧锚定 + continuity ON` 规则的原因。480p 调通构图与运动后再升 720p——分辨率翻倍帧显存也近乎翻倍。

## 七、闭源 API 视频模型接入 ComfyUI

### 7.1 两条接入方式

1. **每家一个节点包**（如 ComfyUI 官方 MiniMax H3 伙伴节点、各厂商插件）：参数最全，但多账号多密钥多套节点。
2. **统一 API 网关节点**（如 Comfyui-zhenzhen、Atlas Cloud 这类 OpenAI 兼容统一端点）：一个 key 跨多家、工作流里换模型名即可；缺点是价格与稳定性受网关影响，商用需自行评估。

> 所有生产级视频 API 都是**异步 task_id + 轮询**，接入自动化要单独封装队列 / 重试 / 状态机，不能当同步 HTTP 调用写。

### 7.2 选型速查（2026-09 公开横评口径，单价仅作量级参考）

| 模型 | 单价量级 | 单段时长 | 核心优势 | 漫剧适配 |
|---|---|---|---|---|
| **Seedance 2.5**（字节） | ~0.3–0.5 元/s | 5–15s | 分镜理解 / 运镜 / 中文叙事最强一档，I2V 优于 T2V，剪映生态打通 | ★★★★★ 分镜逐镜首选 |
| **Kling 3.0 Omni**（快手） | ~0.6–0.9 元/s | 10s，可续写至 2min | 物理运动 / 武侠动作 / 首尾帧 / 续写最强 | ★★★★☆ 动作镜头 |
| **Vidu**（数智新视界） | ~0.3 元/s | 10s | 多主体参考图 I2V 极强，专门锁多角色 | ★★★★☆ 固定 IP 系列 |
| **Wan 3.0** | ~0.25–0.5 元/s | 10–30s | 长单段、多素材参考（10 图+5 视频+5 音频）、试错成本最低 | ★★★★☆ 批量素材 |
| **MiniMax H3** | ~0.4 元/s（本地无成本） | 4–15s | **原生音画同步**、Ref2VA 多参考、可本地私有化 | ★★★★★ 本生产线主力 |
| **Veo 3.1** | ~$0.1–0.4/s | 8s 可延伸 | 电影级质感 + 原生音频 | ★★★☆☆ 关键镜头 / 海外 |
| **Sora 2 / Runway Gen4.5** | ~$0.2–0.5/s | 6–20s | 长叙事 / 镜头控制 / 视频编辑 | ★★☆☆☆ 高预算专用 |

**分镜驱动、逐镜 I2V 的短剧漫剧链路**，公认对参考图/角色资产最友好的是 **Seedance、Vidu、Kling、MiniMax H3** 四家；要数据不出网 + 无限试错，只有 **Wan 与 MiniMax H3**（开源权重）能本地跑。原生音频目前只有 **Veo、MiniMax H3** 第一梯队，其余仍走「出画面 → TTS → 后期对轨」。

| I2I 编辑 | QwenEdit 三参考换人、三视图合成；04-换脸与角色一致性 | **Qwen-Image-Edit 2511（4-step LoRA）** 与 **FLUX.1 Kontext** 两条指令式编辑线；Kontext 多图参考注意别 stitch |
| 角色一致 | 角色板 + 三视图 + 参考注入 | 主角 LoRA + 特写叠 PuLID 的分层策略（本仓库已有换脸目录，可评估） |
| T2V / I2V | H3 导演台多版（通用 / NG / Timeline / T8 曜石）、Multiframe、FunControlNetUnion | Wan2.2-5B 作为**低成本批量 / 试错**补充引擎（Apache 2.0、16G 轻松） |
| 首尾帧 | H3 FLF2V、H3 二采 / Continuum 续接 | Wan2.2 FLF2V 作开源备份，避免单一 API 依赖 |
| 音频 | IndexTTS2 工作台 + 7 份对比工作流（见 `02-漫剧/03-配音流水线/`） | 本轮已覆盖，暂不重复 |
| 门禁 | `h3_lint/` 全链 + CSV 19 字段契约 | 若引入 Wan 线，需另立不依赖 H3 17n+5 帧网格的段长口径 |
