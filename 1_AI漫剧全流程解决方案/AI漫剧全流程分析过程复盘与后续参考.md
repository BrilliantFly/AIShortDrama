# AI漫剧全流程分析过程复盘与后续参考

> **定位**：这份文档记录的不是「方案是什么」，而是「**这套方案是怎么被分析出来的**」——取证路径、纠错记录、验证手段、可复用流程。
> **用途**：以后分析同类 AIGC 链路（工具选型、工作流装配、许可合规、版本归档）时，照第 2 / 3 / 5 节走一遍即可。
> **复盘范围**：2026-11-18 ~ 2026-11-21，`novelist + drama + 前半段漫画 + ComfyUI H3 导演台 (r2v)` 全链路。
> **不是什么**：不是操作手册（见 `H3-vibe-生产线操作手册.md`）、不是设计态方案（见 `漫画前置-H3混合路线-实现方案.md`）、不是审核结论（见 `全流程审核报告.md`）。

## 0. 一句话方法论

**先对齐术语 → 再解析现役资产实证 → 把链路画成可核对的契约 → 用可执行门禁代替口头断言 → 每次误判都留下推翻它的证据 → 最后把过程做成可回溯的版本快照。**

这轮最有价值的产出其实不是那 10 个文件，而是**7 次被证据推翻的初判**和**一套能重复使用的验证门禁**。

## 2. 八条被验证有效的方法

| # | 方法 | 这轮的具体做法 | 为什么值得复用 |
|---|---|---|---|
| 1 | **实证优先于推测** | 所有「工作流怎么接」的结论都从实际 JSON 解析 `timeline_data`，而不是看字段名想当然 | AI 工具链的字段名经常与语义相反，猜一次就会污染后面所有文档 |
| 2 | **术语先对齐** | 用户上传文档证明 vibe 是程序/范式后，才重新查 `vibe-video`、`infinite-creation`、`Nomi` | 没对齐术语就检索，会漏掉一整类工具，得出「现网没有」的错误结论 |
| 3 | **反例驱动纠错** | 7 次误判各留一条「推翻它的证据」，见第 3 节 | 只记结论不记反证，下次遇到同构问题会再犯一次 |
| 4 | **四方交叉核对** | 五份文档 ↔ CSV 19 字段 ↔ 装配脚本 ↔ 示例 JSON 逐项对 | 审核报告里 4 个 A 级问题全部来自「单看一份文档都对、合起来跑不通」 |
| 5 | **可执行门禁代替断言** | `--check-only`、`py_compile`、表格列数脚本、`--compare`、哈希、`--dry-run`、旧路径阻断测试 | 「应该没问题」不可验证；门禁能给出 exit code 和逐条 ERROR |
| 6 | **设计态与实施态分离** | 用户明确「不考虑是否安装 Pillow/ComfyUI」后，删掉安装/适配脚本任务，只写实现方案 | 把部署环境混进设计文档，会让方案在环境变化后整体失效 |
| 7 | **沿链路追到最后一层再判瓶颈** | 商用判断从「出图模型许可」一路追到「H3 Community License」 | 瓶颈常在链路末端，只查中间一环会给出错误的合规结论 |
| 8 | **版本可回溯** | 从会话记录重放 Write/Edit 还原历史快照，并用「全部重放 vs 磁盘当前文件」自检 | 就地修订会覆盖历史；没有快照就没有可核查的版本对照 |

## 3. 纠错记录（最值得反复看的一节）

| # | 初判 | 推翻它的证据 | 纠正后 | 可迁移的教训 |
|---|---|---|---|---|
| 1 | vibe 落在 `genImage` | 解析 6 个 EP001 工作流，`genImage` 始终为空 | 每镜帧挂 `refs` index 1，即 `<Picture 1>` | 空字段 = 未启用，别把「看起来像入口」的字段当落点 |
| 2 | `<Picture 1>` 是角色板 | 同一批 EP001 实证 | `<Picture 1>` 是**每镜起始帧**；2/3/4 才是 SHEET / PLATE / PAIR | 槽位语义必须逐镜对照，不能按编号顺序推 |
| 3 | S004 工作流是默认底座 | 文件内便签写明「由通用02 填充生成，勿当模板复用」 | 默认底座改为通用02；S004 仅作 EP001 格式参考 | **实战样例 ≠ 模板**；先找便签/注释再复用 |
| 4 | vibe 不是现成程序 | 用户上传的 DeepSeek 文档 | 文档里的 Vibe 是代码渲染程序／伞状范式；承认漏查 `vibe-video`、`infinite-creation`、`Nomi` | 用户提供的材料优先级高于现网检索印象 |
| 5 | 商用首选 Qwen-Image 2.1 | 许可证核查：2.1 为 Research License 仅非商用 | 改为 2511（Apache 2.0）+ 基座/2512 分工：基座出底图与板、2511 编辑派生每镜 | 「能力最强」不等于「可用」；许可是硬门槛，要放在选型入口 |
| 6 | 商用瓶颈在出图模型 | H3 Community License 条款（地域、营收、署名、AI 标识、禁蒸馏） | **全链路商用由 H3 决定**，换出图引擎或改在线 API 都绕不开 | 合规判断要覆盖到最后一环，不能停在中间模型 |
| 7 | 2511 只有 3 槽，装不下「底图 + 三张板」 | 区分「单次调用上限」与「工作流上限」 | 两级 2511 串联：Stage 0 T2I 底图 → Pass 1（底图+SHEET+PLATE）→ Pass 2（中间帧+PAIR+空）；`image_1` 永远是被编辑目标图，绝非 SHEET | 接口限制不等于流程限制；先问「能不能拆成多次调用」再判不可行 |

> 另有一条隐性纠错：通用02 底座残留 `960×544`、S004 的 `continuityEnabled=False` 与出片口径不符，装配脚本统一规范化尺寸、`SaveVideo` 前缀与 `continuityEnabled` 继承——**底座也会有脏数据，装配层要做归一化**。

## 5. 后续分析同类问题的 SOP（可直接套用）

| 步 | 做什么 | 验证手段 | 产出 |
|---|---|---|---|
| 1 | **术语对齐**：把每个名词指向的具体东西写下来（是程序？环节？范式？） | 用户材料 > 本地文档 > 现网检索 | 术语表，避免检索方向错 |
| 2 | **读现役资产**：解析本地实际工作流 JSON / skills 文档，不靠命名猜 | 脚本解析 + 打印关键字段 | 实证结论（槽位、帧率、尺寸、 continuity） |
| 3 | **画链路并标契约点**：把每一步的输入/输出/落盘路径写死 | 一张字段契约表 | `shotlist.csv` 之类的数据契约 |
| 4 | **现网核查**：工具、价格、许可证，**标注核查日期** | 官方页面；价格/条款有失效性 | 选型表 + 硬门槛清单 |
| 5 | **写设计态方案**：不碰安装、版本、凭据、显存 | 用户确认「设计态」边界 | 实现方案文档 |
| 6 | **交叉审核**：逐份通读 + 四方对齐 + 实跑门禁，按 A/B/C 分级 | 门禁脚本 + 证据行号 | 审核报告 |
| 7 | **落地**：按决定逐条改，改完立刻实跑验证 | 见下方门禁清单 | 修订版文档 + 脚本 |
| 8 | **归档**：工作区与归档分离；历史版本用记录重放还原 + 哈希自检 | SHA256 / 逐字比对 | 版本目录 + README + 版本说明 |

### 门禁清单（第 7 步照着勾）

- [ ] 字段齐全、列名与脚本读取一致（含 UTF-8 BOM 口径）
- [ ] 帧数网格（17n 或 5+17n）、段长 ≥ 台词朗读时长
- [ ] 路径契约：相对 `input/` 根、三段式、列 ↔ 目录 ↔ 扩展名一致
- [ ] `input/` 资产齐套；根目录不存在时**明确报「检查未执行」**，不静默跳过
- [ ] 01 预览与 02 出片的 `segments / totalFrames / frameRate / continuity` 一致
- [ ] 死列生效（`duration_sec` / `qc_status` 不再只是摆设）
- [ ] 脚本 `py_compile` 通过；示例 JSON 可 `json.load`；节点/连线数与底座一致
- [ ] 文档表格列数一致；跨文档术语、代号、路径口径统一
- [ ] 许可证硬门槛写在**选型入口**，不是附录
- [ ] 哈希核对归档副本 == 工作区当前文件

### 两个容易漏的判断

1. **「不能做」之前先问「是不是单次调用的限制」**——A3 的解法就是把一次 2511 拆成两次。
2. **「改好了」之前先问「有没有门禁能证明」**——这轮每个 A 级闭环都配了一条可复跑的命令。
